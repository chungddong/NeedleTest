Needle 3를 라즈베리파이 5에서 돌려봤습니다

Cactus Compute의 35MB짜리 툴콜링 모델 Needle 3를 직접 만든 테스트셋 92개 쿼리(+추출 16, 임베딩 24)로 측정했습니다. 영어 명령은 꽤 정확하고 0.3~0.4초 안에 답하며 메모리는 100MB 안쪽으로 씁니다. 다만 한국어는 거의 안 되고, 홍보 문구의 “Pi 5에서 4,000 tok/s”는 정확도가 0%인 depth 2에서만 나오는 숫자였습니다.

01테스트셋별 정확도

공식 2비트 20레이어 모델, Python SDK(cactus-needle) 기준입니다. 각 쿼리를 3번 실행한 평균이고, 함수 이름과 인자가 모두 맞아야 정답(exact)으로 셉니다. 자유 텍스트 인자(메시지 본문, 노래 제목 등)는 포함 관계면 정답으로 봤습니다.

신뢰도 게이트 적용 정확도 (confidence ≥ 0.4만 실행)

raw 모델이 낸 호출 그대로 · 게이트 confidence 0.4 미만은 거절로 처리 · strict 게이트에 더해 SDK가 “근거 없음(ungrounded)”이나 부정문으로 표시한 호출을 버림 (공식 환경 테스트 하네스의 규칙과 동일)

02깊이(레이어 수)와 정확도·속도

Needle 3는 가중치 하나로 2~20레이어 중 원하는 깊이만 돌릴 수 있습니다. C 런타임의 --depth 옵션으로 같은 35MB 파일을 깊이만 바꿔 측정했습니다(4스레드). 얕게 돌리면 빨라지지만 6레이어 이하에서는 거절 외에는 하나도 못 맞혔고, 쓸 만한 구간은 18~20레이어였습니다.

정확도 (게이트 적용 exact)

응답 지연 중앙값 (ms)

prefill/decode는 엔진이 응답마다 보고한 tok/s의 중앙값. --depth는 전체 가중치를 그대로 올리므로 메모리는 깊이와 상관없이 73.6MB로 같았습니다. depth 2~6에서 refusal 세트가 100%인 건 모든 요청을 거절했기 때문입니다.

03속도와 처리량

스레드 수별 지연 (depth 20, 서버 1개)

2~3스레드가 4스레드보다 빨랐습니다. 이 Pi는 다른 서비스도 돌고 있어(load avg 0.7~3) 4번째 코어를 두고 경합한 영향으로 보입니다.

동시 처리량 (초당 쿼리)

서버 여러 개를 띄워 4코어를 나눠 쓴 경우. 처리량은 늘지만 개별 응답은 느려지고 메모리는 서버 수만큼 늘어납니다.

등록한 툴 개수에 따른 변화

테스트용 툴 11개에 상관없는 조회용 툴을 추가로 붙여 basic·args·refusal 55개 쿼리를 다시 돌렸습니다. 툴이 30개를 넘으면 정확도가 91%에서 65% 근처로 떨어졌습니다. 툴 설명이 길어질수록 매 요청의 prefill이 길어져 지연도 늘어납니다.

04메모리 사용량

프로세스 최대 상주 메모리(VmHWM)입니다. C 런타임만 쓰면 74MB, Python SDK를 거치면 인터프리터 몫이 더해져 112MB입니다. 16GB Pi에서는 부담이 거의 없는 수준이고, 1~2GB 보드에서도 충분히 올라갑니다.

W4 항목은 공개 빌드 도구(needle build --layers N)로 직접 만든 4비트 모델입니다. 공개 도구는 4비트 내보내기만 지원해서, 공식 2비트 파일보다 레이어당 크기가 큽니다.

05구조화 추출과 임베딩

구조화 추출 (16건, 필드 54개)

임베딩 의도 라우팅 (24쿼리, 8개 의도)

06테스트하며 발견한 문제

  • 주의SDK의 근거 검사가 올바른 변환을 버립니다

    “2시간 타이머” → minutes=120, “오후 7시 알람” → "19:00"처럼 모델은 맞게 변환했는데, SDK가 이 값을 원문에 없는 값(ungrounded)으로 표시합니다. 공식 하네스 규칙(strict)을 따르면 이런 정답 8건이 버려지고, agent.run()의 기본값 strict=True에서도 실행이 막힙니다. 게이트 정확도 80%가 strict에서는 73%로 내려간 이유가 대부분 이것입니다.

  • 주의시간 형식 정규식이 5초 지연을 만듭니다

    “Set the alarm for 5:45”, “plz set alarm 8:00”에서 모델은 5:45를 쓰려 하는데 스키마의 HH:MM 정규식은 앞자리 0을 요구합니다. 문법 제약 디코딩이 512토큰을 다 쓰고 4.4~5.1초 뒤 빈 결과(token budget exhausted)를 냅니다. 패턴을 H:MM도 허용하게 바꾸거나 설명으로 형식을 안내하는 편이 낫습니다.

  • 미지원한국어는 사실상 안 됩니다

    한국어 12개 중 맞춘 건 “10분 타이머”와 “피자 주문해줘”(거절) 2개뿐입니다(C 런타임에서는 0~1개). 대부분 confidence 0.1 미만으로 거절했고, “재즈 틀어줘”는 get_weather(city="틀어줘"), “아침 7시 알람”은 7분 타이머로 바뀌었습니다. 한국어 서비스라면 앞단에서 영어로 번역하거나 파인튜닝이 필요합니다.

  • 약점없는 기기를 비슷한 툴로 처리합니다

    “침실 선풍기 켜줘”를 조명 켜기로 실행했고 confidence가 0.79라 게이트로도 걸러지지 않습니다. 툴 설명에 “조명 외에는 사용 금지”라고 적었는데도 그랬습니다. 툴 목록을 확장할수록 이런 오매핑이 늘었습니다(툴 51개에서 “버스로 박물관 가는 길” → 버스 도착 조회, “기차역까지 걸어서” → 교통정보 조회).

  • 약점얕은 모델은 불안정합니다

    공개 빌드 도구로 만든 4레이어 모델은 한국어 입력 등에서 깨진 UTF-8을 출력해 SDK 워커 프로세스가 4번 죽었고, 13개 쿼리는 토큰 한도를 다 쓰고 끝났습니다(자동 재시작 후 계속 측정). 정확도도 18%로, 8MB급 초경량 구성은 툴콜링 용도로 쓰기 어렵습니다.

  • 양호영어 기본 명령과 추출은 믿을 만합니다

    basic·args 세트는 95%, 다중 호출 90%, 구조화 추출 필드 98%였습니다. 같은 입력·같은 시스템 프롬프트에서는 3회 반복 결과가 모두 같았습니다(결정적). 실행할 때마다 1~2%p 차이가 난 건 SDK가 시스템 프롬프트에 현재 시각을 넣기 때문입니다.

07틀린 케이스 전체

공식 모델(Python SDK)에서 게이트 또는 strict 기준으로 틀린 쿼리입니다.

08측정 방법

테스트셋: 툴 11개(날씨, 타이머, 알람, 메시지, 전화, 음악, 길안내, 일정, 조명, 온도, 볼륨)에 대해 basic 20 · args 20(단위·enum·시간 변환·상대 날짜) · casual 15(구어체·오타) · multi 10(한 문장 두 동작) · refusal 15(툴 밖 요청·부정문) · korean 12. 기준 날짜는 2026-10-01이고 “tomorrow”는 10-02로 채점했습니다.

지연은 complete() 호출 한 번의 벽시계 시간(리셋 제외)이며 첫 쿼리 워밍업은 뺐습니다. 측정 중 SoC 온도는 58~75°C였고 스로틀링 플래그(get_throttled)는 내내 0x0이었습니다. 각 모델 사이에 60°C 아래로 식을 때까지 기다렸습니다. 텔레메트리는 NEEDLE_TELEMETRY=0으로 끄고 측정했습니다.
